# Decision Log

**Updated approach:** The previous approach used Claude to match invoice descriptions to contract services and then saved those mappings. Although the saved files could be reused for the existing data, the matching process itself was not fully reproducible from a clean clone and could not reliably handle unseen descriptions in a blind test without calling Claude again. I therefore replaced Claude-based service matching with deterministic local Python. The Python matcher compares every invoice description with the services in the relevant contract. It assigns a service only when the evidence is sufficient; otherwise, it returns `UNKNOWN` or `UNSURE`. This allows it to process new descriptions without relying on a saved mapping. Earlier Claude matches were used only as a development reference, not as correct answers, matching rules, or final outputs. The pipeline does not require Claude, an API, or saved matching results.

| Issue | Decision |
| --- | --- |
| Hospital coverage | Hospital 1 is the labeled development and evaluation dataset. The final submission contains Hospitals 2-5. The same extract, match, audit, and validation stages process all five hospitals, with hospital-specific contract rules where required. |
| Service matching | Local Python normalizes descriptions, expands a controlled abbreviation vocabulary, and scores services extracted from the relevant contract. Service text is the primary evidence. Units and exact documented prices can only break ties between textually plausible candidates; the matcher never selects the service with the nearest price. |
| Unclear services | `UNKNOWN` means the description contradicts the available contract services or identifies an unlisted service. `UNSURE` means there is not enough information to choose confidently between plausible candidates. Neither result is forced to a contracted service. |
| Labels | Hospital 1 labels are read only by the evaluation function after predictions have been written. They are not used by rule extraction, service matching, auditing, or submission generation. Hospitals 2-5 have no supplied labels. |
| Hospital 3 amendments | All three Hospital 3 contract documents are extracted together. Amended rates are selected by service date, and services introduced in 2025 are not treated as eligible before their effective date. |
| Volume discounts | For each service, usage is counted across all patients in date order. Hospitals 1, 2, 3, and 5 require this; Hospital 4 is unclear, so I use the same approach. The discount starts on the line after the threshold is crossed. |
| Hospital 5 exclusions and pricing context | The contract was unclear about whether exclusion windows apply before, after, or on both sides of the service date. I checked both before and after for the same patient, including the first and last day of the stated window. Facility and plan-tier values come from the corresponding source invoice and are applied only after a service has been selected from textual evidence. |
| Repeated invoice IDs | Some invoice IDs were used for more than one invoice record, so the invoice ID alone was not always enough to correctly connect line items with the corresponding patient and invoice details. I used the supplied JSONL files because they store each invoice together with its patient details and line items. This allowed me to preserve the correct relationships when checking duplicate charges and exclusions. |
| Malformed dates | Some service dates were invalid, so I could not verify whether the services occurred within the contract period. I kept these date errors flagged, but still calculated provisional expected totals when the correct price and quantity could be determined without the service date. |


**Evaluation and limits:** Hospital 1 has 913 labeled invoices. The pipeline identifies all 58 flagged invoices with no false positives or false negatives, and 912 of 913 invoices have the exact labeled error-category set. The remaining mismatch is caused by an incomplete service description that was matched to a specific service even though a key specialty word was missing. Confidence scores describe evidence strength, not calibrated probabilities. Hospitals 2–5 do not include correct answers for comparison, so their accuracy cannot be measured. I only verify that the pipeline processes all their data and produces valid outputs.

**Reproducibility:** `src/run_all.py` regenerates contract-rule JSON, service matches, five hospital prediction files, and the combined Hospital 2-5 submission from repository inputs. It then validates line and invoice coverage, output structure, flags, categories, totals, confidence values, and submission composition. The same work can also be run as three explicit stages with `extract_rules.py --all`, `match_services.py --all`, and `audit_invoices.py --all`, followed by `validate_all.py`. Running the pipeline uses only Python and the repository files. It does not call any model or API, and it does not reuse matches previously created by Claude.

**Next steps:** If labels become available for Hospitals 2–5, I will use them to measure accuracy. I would also review unclear contract rules and improve how the matcher rejects incomplete descriptions.
